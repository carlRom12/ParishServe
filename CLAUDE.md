# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ParishServe — a parish services website for Our Lady of the Gate Parish (a capstone project). Plain HTML5/CSS3/vanilla JS frontend with a PHP + MySQL backend for accounts (registration + email OTP, login, password reset), the six public request forms, announcements, and the admin portal (requests, donations, announcements, staff accounts). There is no build step, package manager, linter, or test suite.

## Running

Served by XAMPP (Apache + PHP 8.0 + MariaDB 10.4) from `C:\xampp\htdocs\ParishServe1`:

- App: `http://localhost/ParishServe1/index.php` (public home page); parishioner portal starts at `dashboard.html`, staff at `login.html` → `admin-dashboard.php`
- Start/stop Apache and MySQL via `C:\xampp\xampp-control.exe` (or `apache_start.bat` / `mysql_start.bat` in `C:\xampp`)
- PHP syntax check: `C:\xampp\php\php.exe -l <file>.php` (there is no Node on this machine, so JS can't be syntax-checked from the CLI — load the page in headless Chrome and look for console errors)
- DB shell: `C:\xampp\mysql\bin\mysql.exe -u root parish_serve` (root, no password — see `config.php`)
- Visual check: `chrome.exe --headless=new --user-data-dir=<temp dir> --screenshot=<out.png> --window-size=1280,900 <url>` (a separate `--user-data-dir` is needed when Chrome is already open); add `--enable-logging=stderr --dump-dom` to see console errors and the rendered DOM

HTML pages can also be opened via `file://`, but everything that talks to PHP (auth, uploads, feeds) is skipped there.

## Architecture

**Pages are static `.html` files with duplicated layout.** The site was originally PHP templates (`includes/header.php`, `sidebar.php`, `topbar.php`, `footer.php`, `icons.php`); those includes were expanded inline into each page. Consequences:
- Navigation, sidebar, header, and icon SVG markup are repeated in every page — a nav/layout change must be applied across all pages (including the six `.php` final steps, which are the same markup with a PHP header).
- Code comments sometimes still reference old `.php` names (e.g. "see wedding-request-step2.php"); read those as the corresponding `.html` page.
- The topbar user chip ships as a guest (`data-session-name` / `data-session-initial` / `data-session-role`) and the sidebar link as `data-session-auth-link`; `assets/js/session-user.js` (loaded right before `responsive.js`) fills them from `session-user.php` and turns the link into "Log in" for visitors. Never hardcode a person's name, role or notification count into a page.

**The admin portal (`admin-*.php`) is rendered by PHP.** Every admin page and admin endpoint first requires `includes/auth-guard.php`, which re-reads the signed-in user from `users` on each request (role changes and suspensions apply immediately) and admits Admin + Super Admin. Set `$psGuardRoles` before requiring it to narrow that (e.g. `['Super Admin']`), and `$psGuardJson = true` in fetch endpoints to get 401/403 JSON instead of a redirect. It sets `$userFirstName`/`$userRole` and provides `ps_current_user_id()`, `ps_current_role()`, `ps_is_super_admin()`, `ps_csrf_token()`, `ps_require_post_csrf()` and `ps_json()`. Each page then sets `$pageTitle`, `$pageCss` (string or array), `$activeNav`, and requires `includes/header.php` (emits the `csrf-token` meta) → `includes/admin-sidebar.php` (Accounts link only for Super Admin) → (inside its header section) `includes/topbar.php` (pending-count bell) → `includes/footer.php`. Icons come from `ps_icon($name, $class)` in `includes/icons.php` — the same SVGs the `.html` pages carry inline; add new icons there. The 7 request pages (`admin-wedding-requests.php`, `admin-baptism-requests.php`, `admin-confirmation-requests.php`, `admin-funeral-requests.php`, `admin-counseling-requests.php`, `admin-mass-intentions.php`, `admin-facility-reservations.php`) only set `$requestType` and require `includes/admin-request-page.php`; `?ref=<reference>` pre-fills their search (how the dashboard, calendar and reports link to one request), and the sidebar builds their links from `PS_REQUEST_TYPES` (`plural`, `page`). `admin-calendar.php` is the staff month view of every dated request with conflicts flagged; `admin-reports.php` is the read-only date-range report with `?export=csv|pdf` (`includes/reports.php`; the PDF comes from the dependency-free `includes/pdf.php`).

**`includes/request-types.php` is the single source for request data**: the 7 request types (table, name/date/time/end/subtype SQL expressions, admin page, icon, calendar category, booking resource and length), the status pipeline and labels, `PS_DOCUMENT_CHECKLISTS`, query helpers (`ps_fetch_requests($conn, $filters)` UNIONs the 7 tables, filtered by `type`/`contact`/`from`+`to`+`basis`/`limit`; `ps_fetch_donations()`, `ps_count_requests_by_status()`, `ps_pending_counts()` with a per-type `byType`, `ps_fetch_documents()`, `ps_fetch_public_bookings()`) and the scheduling rules. The pipeline is strict: `ps_next_statuses()` allows only the next step or `rejected`, and `completed`/`rejected` are final. **Schedule conflicts** are overlapping time blocks on the same date between booked requests (`PS_BOOKED_STATUSES`) that need the same `resource` — the church (wedding, baptism, confirmation, funeral), the counseling office, or the same facility. A block runs from the request's time for its type's `minutes` (facility reservations use their end time); Baptism and Confirmation are `group` ceremonies (same-type bookings share a slot) and Mass Intentions never conflict. `ps_bookings_on()`, `ps_schedule_conflicts()` and `ps_mark_conflicts()` implement this for the public form check, the booking hint, the admin Update window and the admin calendar — change the rules there only. Approved/Scheduled requests must have a date and time (`PS_SCHEDULE_STATUSES`). The request pages, `admin-donations.php`, `admin-dashboard.php`, `admin-calendar.php`, `admin-reports.php` and `admin-announcements.php` all read real rows (announcements via `includes/announcements.php`).

Admin client behavior is data-attribute driven in `main.js`: `initAdminTableFilters()` (`data-admin-row` with `data-type`/`data-status`/`data-search`, type tabs, status select, search, empty state), `initAdminModals()` (`data-modal-trigger` copies the button's `data-*` into `[data-modal-field]`s; `data-docs` JSON renders the document checklist; `data-allowed-statuses` disables every status but current/next/rejected; `data-proof` previews a proof of payment; a `data-modal-schedule="<endpoint>"` fieldset is read-only on final records, required for Approved/Scheduled, and previews that day's bookings and overlaps) and `initAdminDelete()`. A `data-admin-form="<endpoint>"` form POSTs as FormData (files included) with the CSRF token (plus `docs` as JSON) and only updates the row and toasts after `{ok: true, message, row}` — `row` carries `status`/`statusLabel`/`statusClass`/`type`, `fields` for `[data-row-field]` cells, and `data` to refresh on the trigger; `reload: true` instead reloads the page and shows the message there. `data-admin-delete="<endpoint>"` buttons confirm, POST `action=delete` + `data-id`, and remove the row on success. Endpoints: `admin-update-request.php` (requests — status, remarks, documents and `event_date`/`event_time`/`event_end`, answered 409 with `conflicts` on an overlap — and donations via `type=donation`; only after the commit does it email the parishioner through `includes/notifications.php`, email only, and say in the message whether it went), `admin-schedule-check.php` (GET overlap preview for the Update window), `admin-save-announcement.php` (`action=save|delete`), `admin-update-account.php` (Super Admin only), `pending-count.php` (polled by `initNotificationPoll()`). There are no screen-only "mock" saves; don't add any.

**Asset loading convention** (per page, in this order): `style.css` → page-specific CSS → `responsive.css?v=N`; scripts at the end of `<body>`: `frontend.js` → `main.js` → page scripts → `session-user.js` → `responsive.js?v=N` (some redesigned pages load only their own script plus the last two). Bump a script's `?v=` query when you change it. Several CSS files are shared across sacraments (e.g. baptism/confirmation pages reuse `wedding-request.css`, `confirmation-layout.css`).

**JS is IIFE-per-feature, activated by `data-*` attributes** rather than page checks — e.g. `data-wizard-step-form`, `data-upload-flow`, `data-confirm-toggle`, `data-max-size-mb`, `data-datepicker`, `data-carousel`, `data-service-schedule`. To reuse a behavior on a new page, add the attribute. `responsive.js` injects the mobile header/nav drawer around `.ps-sidebar`/`.ps-main` and wraps tables/calendar grids in scroll containers at runtime.

**The six public request forms submit to the server** (no login needed — requests are tracked by reference number + contact number). Earlier steps are `.html`; the final page of each is `.php`:
- Wedding: `wedding-request.html` → `wedding-request-step2.html` (documents) → `wedding-request-step3.php` (review; `wedding-review.js`)
- Baptism: `baptism-request.html` → `baptism-request-step2.php` (document + inline review; `baptism-upload.js`)
- Confirmation: `confirmation-request.html` → `-step2.html` → `-step3.html` (document) → `confirmation-request-step4.php`
- Funeral: `funeral-request.html` → `-step2.html` → `-step3.html` (document) → `funeral-request-step4.php` (all steps run `funeral-request.js`)
- Mass intention: `mass-intention-request.php` — one page whose three steps are panels (`mass-intention-request.js`)
- Donation: `donations.html` (hub with about/guidelines/how tabs) → `donation-request.php`

How it fits together:
- Each final page starts with `ps_handle_request_form('<flow>')` and prints `ps_request_form_fields()` (one-time submit token + the last attempt's error list) inside its form. `PS_REQUEST_FORMS` in `includes/request-forms.php` defines each flow's `steps` and field rules; a field's `step` indexes `steps`, fields on the final page are read from POST and earlier ones from the `ps_draft` JSON. Renaming, adding or moving an input means updating that array.
- `frontend.js` detects the flow from the filename, keeps fields in sessionStorage under `parishserve-draft-<flow>` (mass-intention / donations for the last two), and navigates plain steps via `location.href`. Forms marked `data-wizard-step-form`, `data-baptism-upload` or `data-multi-step` submit themselves: `initWizardStepForm()` in `main.js` copies the draft named by `data-draft-key` into `ps_draft` and submits; `baptism-upload.js`, `funeral-request.js` and `mass-intention-request.js` do the same in their own code. `frontend.js` also fills `confirmation-request-step4`'s review rows by index-matching `.wr3-review-row strong` — reordering those rows means updating its field list.
- Documents: inside `form[data-upload-flow="<flow>"]`, `request-uploads.js` uploads each file to `upload-document.php` the moment it's chosen (staged per session by `includes/uploads.php`; a staged document drops its input's `required`). The final submit moves staged files to `uploads/<type>/<reference>/` and records them in `request_documents` (donations: `donations.proof_of_payment`). `[data-uploaded-docs="<flow>"]` lists what the server holds. A page's own "Remove File" button dispatches `ps:request-remove` on the input to discard the server copy. `uploads/` is closed to the web; staff open files through `admin-file.php`.
- Schedule: before inserting, `ps_request_schedule_errors()` refuses a date + time that overlaps a booked request (reported on the form's `schedule_step`). Only the funeral form asks for a time today; wedding and baptism requests get their time — and the check — when staff approve them. `assets/js/booking-hint.js` lists a chosen date's taken times under any `input[data-booking-type="<type>"]` (from `booking-availability.php`), and with `data-booking-time="<time input name>"` marks an overlapping time invalid. Each form also stores its email address in the row's `contact_email`, where status emails go.
- Success → 303 to `request-confirmation.php?ref=<reference>` (viewable only by the submitting session; clears the draft). Validation problems → 303 back to the final page, which lists them.
- Not wired to the backend: `counseling-request.html` (no `PS_REQUEST_FORMS` entry) and the orphaned `mass-intention-request-step2.html`/`-step3.html` (superseded by the one-page form; nothing links to them).

**Public data feeds** — pages hold no sample content, so everything below is empty until real submissions/approvals/posts exist:
- `calendar-events.php?month=&year=`: approved/scheduled/completed bookings for the 6-week grid, anonymous (type, label, time, status; counseling excluded). Used by `calendar.js`, `service-schedule.js` (the `*-schedule.html` tabs, configured by `data-service-schedule` on `#confSchedGrid`), `dashboard-revamp.js` (Today at the Parish), and `announcements.js` (Upcoming Parish Events).
- `booking-availability.php?type=&date=`: the times already booked that day in the place that request type uses (anonymous; public types only), for `booking-hint.js`.
- `announcements-data.php`: published announcements. `announcements.js` renders `announcements.html` (featured carousel, list, Important Notices = category "Notices") and fires `ps:announcements-rendered`, which `main.js`'s carousel, category tabs, search and Load more listen for. The dashboard's Parish Updates card shows the newest (featured first).
- `dashboard-data.php`: the signed-in user's latest requests and counts (`users.mobile_number` = `contact_number`); `dashboard-revamp.js` shows a "Log in to see your requests" prompt otherwise.
- `session-user.php`: who is signed in (name + role only).

**Auth backend:**
1. `register.html` posts to `login_register.php` → validates, inserts into `users` with a hashed password and hashed 6-digit OTP (`PS_OTP_TTL_SECONDS` = 180s, defined in `includes/otp-mailer.php`, which also builds the email's "expires in N minutes" text from it), emails it via `includes/otp-mailer.php` (bundled PHPMailer, Gmail SMTP from `includes/mail-config.php`), sets `$_SESSION['pending_user_id']`, redirects to `verify-otp.html`.
2. `verify-otp.html` posts `verify` or `resend` to `verify-otp.php`, which sets flash messages in the session and 303-redirects back (or to `login.html` on success).
3. `login.html` posts to `login.php`: `password_verify()`, requires `status = 'Active'` and `email_verified = 1` (unverified accounts are sent on to `verify-otp.html`), regenerates the session id and sets `user_id`/`user_role`/`user_name`. Admin/Super Admin go to `admin-dashboard.php`, Parishioners to `dashboard.html`. `logout.php` (every sidebar's Log out link) clears the session.
4. Password reset: `forgot-password.html` → `forgot-password.php` (says "No account found" for unknown emails — a deliberate product choice) → `verify-reset-otp.html`/`.php` → `reset-password.html`/`.php`. It uses its own `reset_otp_hash`/`reset_otp_expires_at`/`reset_otp_attempts` columns (never the registration OTP), a 60s resend cooldown (`otpSentRecently()`), 5 wrong tries burn the code, a correct code is consumed atomically, and the verified step stays open for 10 minutes.
5. Because pages are static HTML, flash messages/old input reach the page via `auth.js` fetching `auth-state.php?page=<register|verify-otp|login|forgot-password|verify-reset-otp|reset-password>` (JSON; values are consumed/unset on read; a `redirect` key sends the visitor away from a step they can't use yet).

The parishioner pages themselves have no auth guard. Validation rules are duplicated between the browser (input attributes, `main.js`, page scripts) and PHP (`includes/request-forms.php`, the auth handlers) — PH mobile format `^09\d{9}$`, password ≥ 8 chars (registration and reset), name regex, future/past date rules, file types and sizes; keep both sides in sync.

## Database

- The schema history is `database/migrations/` — additive, re-runnable SQL, applied in order: `C:\xampp\mysql\bin\mysql.exe -u root parish_serve < database\migrations\000-users.sql`, then 001, 002, 003, 004. 000 records the `users` table (it predates the migrations); 001 adds the 7 request tables + `donations` + `request_documents` and the `reset_otp_*` columns; 002 adds the `details` JSON column everywhere, a nullable Confirmation date, the Mass Intention type enum and `request_documents.original_name`/`uploaded_at`; 003 adds `announcements`; 004 adds `contact_email` to the 7 request tables and `donations` (backfilled from `details`) plus date/status indexes for conflict checks. There is no full schema dump (the old demo `database/schema.sql` is gone) — put any new change in the next numbered file and run it.
- Requests link to parishioners by `contact_number` (= `users.mobile_number`) + a server-generated `reference_no` (`<PREFIX>-<YEAR>-<NNNN>`), not a `users.id` FK. All request tables share one status pipeline `submitted → under_review → approved → scheduled → completed` (or `rejected`) so they can be UNIONed. Whatever a form collects beyond a table's columns is kept in that row's `details` JSON (`{"Label": "value"}`), shown to staff in the Update modal.
- Announcements with a future `posted_date` are scheduled: staff see them, `announcements-data.php` and `announcement-image.php` hide them until that day. Images are PNG/JPG only (never SVG), stored in `uploads/announcements/`.
- There is no seed data: requests, donations and announcements only come from the real forms and admin UI. Super Admin accounts are created directly in the database (no UI); Admins are made by a Super Admin on `admin-accounts.php`, from accounts that have verified their email.

## Content caveats

- Parish office hours and phone, sacrament fees, guidelines, the Mass times offered in the forms and the GCash QR (still a placeholder, flagged on the donation page) are static page content, not data.
- `includes/mail-config.php` contains real SMTP credentials — never print, copy, or move them into other files.
